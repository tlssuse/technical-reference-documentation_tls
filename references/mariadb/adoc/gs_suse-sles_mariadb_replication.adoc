== Key take aways

* {sles-provider-website}[{sles-provider}] and {mariadb-website}[{mariadb-provider}] deliver enterprise-supported open source software for mission-critical applications.

* A primary-replica database architecture improves read performance, data consistency, high availability, and disaster recovery.

* Easily deploy a primary-replica database topology with {mariadb-website}[{mariadb}] on {sles-website}[{sles}].



== Introduction

This guide provides step-by-step guidance for deploying a primary-replica database topology with {mariadb-long} on {sles-long}.
The topology relies on maintaining copies of a database across multiple hosts, replicating data from an identified primary to one or more secondaries.
By distributing the data and workloads, organizations can deliver improved performance, maintain data consistency, and support high availability and disaster recovery requirements.

{mariadb-website}[*{mariadb-long}*] is a high-performance, open source relational database management system (RDBMS).
It began as a community-developed fork of MySQL to ensure the software remains free and accessible under the GPL license.

{mariadb} uses native storage engines to provide flexibility for diverse workloads.
Some highlighted storage engines are:

* InnoDB engine — ensures ACID compliance and transaction support.
* Aria — offers a crash-safe alternative to MyISAM.
* MEMORY — stores data in RAM for high-speed lookups.
* Spider — provides a partitioned, federated database solution.

Numerous database connectors also support the open source ecosystem.
This allows seamless integration with applications built in Python, Java, C++, and other languages.

{mariadb} supports database replication in a primary-replica topology, allowing organizations to see improved availability, minimized downtime, and increased performance.



{sles-website}[*{sles-long}*] provides a robust and reliable foundation for {mariadb} deployments, making it a compelling choice for businesses that need enterprise-grade stability and support.
SUSE offers a 13-year lifecycle (10 years general support and three years extended support).
This gives organizations the confidence to run mission-critical applications without frequent, costly upgrades.

{sles} features broad hardware and cloud platform support.
It also provides access to a curated collection of securely packaged, maintained, and supported open source applications, including {mariadb} Server.
SUSE also delivers world-class support services, leveraging deep expertise in business-critical environments and a long history of working with demanding applications, such as SAP.
This ensures that customers receive responsive and expert assistance.


In addition, organizations can deploy {mep-website}[*{mep-long}*] on {sles-long}, combining a secure database platform with a stable operating system optimized for mission-critical workloads.
This dual-vendor architecture ensures enterprises benefit from access to advanced, production-ready features like MaxScale for high availability, automated backups, and enhanced security compliance alongside the renowned reliability and compliance standards of {sles-long}.
Furthermore, this approach provides organizations with clear, comprehensive support pathways from both operating system and database engineering experts, mitigating operational risks.


Together, SUSE and {mariadb} deliver open source innovation, reliability, performance, and scale.

* *Database administrators (DBAs)*: DBAs manage database topology.
They would use the guide to implement {mariadb} replication for asynchronous or semi-synchronous primary-replica configurations to ensure that database services remain highly available.

* *System administrators*: System administrators handle underlying OS infrastructure.
They would use this guide to deploy and configure {mariadb} on {sles}.

* *IT architects and engineers*: Infrastructure designers must meet strict business continuity requirements.
They would use the guide to architect replication strategies across environments.
For example, they could configure local clusters within a single data center or stretched metro clusters across multiple buildings to ensure data integrity and seamless failover.

They can see how {sles} and {mariadb} replication support business continuity.
This combination helps meet Service Level Agreements (SLAs) for mission-critical applications.

* *Application developers and ISVs*: Developers ensure applications stay responsive during server outages.

* *IT consultants and service providers*: Enterprise architects implement high availability blueprints.
These best practices deliver disaster-resilient environments that protect clients from data loss and outages.



== Architecture

image::SUSE-MariaDB-primary-replica.png[title="Basic Primary-Replica Topology", Basic Primary-Replica Topology, scaledwidth=90%]

To implement this architecture, you need at least two host systems — one to host the primary database and one to host the replica.
These can be physical machines, virtual machines, or cloud instances.

For the purposes of this guide, the following system specifications are adequate:

* Processor: 2 CPUs or vCPUs

* Memory: 4 GB

* Storage: 50 GB

* Network: 1 Gbps Ethernet or better

You can find additional sizing guidance in the product documentation.
Both SUSE and {mariadb} offer consulting and professional services to help you design environments for enterprise scale.



== Preparing the hosts

Set up your primary and replica host systems.

. Install {sles-long} on each host. +
Detailed installation guidance is available in the {sles-docs}[{sles-long} Documentation].

. Configure each host with an appropriate hostname and IP address for your environment. +
For example:
+

|===
|Hostname
|Role
|IP address

|host1
|primary
|192.168.12.159

|host2
|replica

. Register each host with a valid subscription to ensure you get product updates and technical support.

. Apply available patches and updates.

. Ensure TCP ports 3306 (MariaDB) and 22 (SSH) are open in the firewall (see {sles-docs-firewalld}[Introduction to firewalld]).



== Installing {mariadb}

Perform the following steps on both the primary and replica hosts.

////
// The `mariadb` packages are in the standard `SLE-Product-SLES-16.0` repository, there is no need to add this module.

. Enable the server application module.
+
[source, console]
----
suseconnect -l sle-module-server-applications/16/x86_64
----
////

. Install the {mariadb} server and client packages from the {sles-provider} repositories.
+
[source, console]
----
sudo zypper install mariadb mariadb-client
----
+
[NOTE]
====
During installation, you may see messages stating that an empty database will be created at first start and that you should set a password for the MariaDB root user.
====

. Enable and start MariaDB.
+
[source, console]
----
systemctl enable --now mariadb
----
+
[source, console]
----
systemctl status mariadb
----
+
[listing]
----
mariadb.service - MariaDB database server
     Loaded: loaded (/usr/lib/systemd/system/mariadb.service; enabled; preset: >
     Active: active (running)
...
----

. Secure MariaDB with a good root user password by using one of the following options:
+
* Set the password with the command:
+
[source, console]
----
/usr/bin/mariadb-admin -u root password 'password123'
----
+
[IMPORTANT]
====
Be sure to replace 'password123' with your own secure password.
====

* Alternatively, execute the secure installation script:
+
[source, console]

+
This interactive script prompts you to select security configuration options. including:

* removing MariaDB root accounts that are accessible outside the local host
* removing anonymous user accounts
* removing the test database
--
+
[NOTE]
====
The `mariadb-secure-installation` script is also symlinked as `mysql-secure-installation` to maintain compatibility.
====


== Configuring the primary database

Perform the following steps on the primary host.

. Log into the primary host.

. Edit the global MariaDB configuration file, `/etc/my.cnf.d/server.cnf`, with the following options:
+
[listing]
----
[mariadb]

# --- Basic Server Settings ---
# Unique ID for this primary server in the topology (1 to 4294967295)
server-id = 1

# --- Binary Logging & Replication Settings ---
# Enables binary logging and defines the base filename
log-bin = mysql-bin

# Enforces row-based logging, required for data integrity across replicas
binlog-format = ROW

# Sets the primary replication domain ID for Global Transaction Identifiers (GTID)
gtid-domain-id = 1

# Ensures changes received from any up-stream hosts are logged to this binlog
# (Uses modern "log-replica-updates" syntax applicable to MariaDB 11.8+)
log-replica-updates = 1

# --- Log Maintenance & Sizing ---
# Automatically purges logs older than 7 days (defined in seconds)
binlog-expire-logs-seconds = 604800

# Limits the maximum size of a single binlog before rotating
max-binlog-size = 100M

# --- Data Integrity & Crash Safety (ACID) ---
# Synchronizes the binary log to disk after every single commit
sync-binlog = 1

# Flushes InnoDB transactions directly to disk at commit for crash-safety
innodb-flush-log-at-trx-commit = 1

# --- Security & Networking ---
# Binds MariaDB to listen only on your chosen internal network IP address
bind-address = 192.168.12.159
----
+
[TIP]
====
Be sure to set `bind-address` to the IP address of your primary host.
Alternatively, you can set `bind-address = 0.0.0.0` to enable MariaDB to listen on all configured IP addresses of the host.
====

. Restart the MariaDB service for changes to take effect.
+
[source, console]
----
sudo systemctl restart mariadb
----

. Grant access to the 'replica' user.

.. Log into the MariaDB server.
+
[source, console]
----
mariadb -u root -p
----
+
Provide your secure, root password when prompted.
+
When you are successfully logged in, you should see the MariaDB command prompt (`MariaDB [(none)]>`).

.. Create the 'replica' user.
+
[source, console]
----
CREATE USER 'replica'@'%' IDENTIFIED BY 'replica-password';
----
+
Be sure to replace 'replica-password' with a secure password.
+
[TIP]
====
User accounts take the form 'username'@'hostname'.
Using quotes around user and host names is good practice, though they are only required when using special characters or wildcard characters.
The `%` wildcard is often used to match multiple hosts.
In the example command, `'replica'@'%'` means that the 'replica' user and connect to the database from any host.
For better security, you can limit the host to the host name or IP address of the replica host or to a range of addresses.
====

.. Grant replication privileges to the 'replica' user.
+
[source, console]
----
GRANT replication slave ON *.* to 'replica'@'%';
----

.. Flush privileges for this change to take effect.
+
[source, console]
----
flush privileges;
----

.. Log out of the MariaDB server.
+
[source, console]
----
quit
----



== Configuring the secondary database

Log into the replica server and perform the steps below.

. Edit the global MariaDB configuration file, `/etc/my.cnf.d/server.cnf`, with the following options:
+
[listing]
----
[mariadb]
# --- Basic Server Settings ---
# A completely unique server ID distinct from the primary node
server-id = 2

# Protects the replica data from accidental writes by applications/users
read-only = 1

# --- Binary Logging & Replication Settings ---
# Keeps binary logging active on the replica for flexible failovers/backups
log-bin = mysql-bin
binlog-format = ROW

# Tracks the exact matching replication group domain ID from the primary
gtid-domain-id = 1

# Logs replica updates so it can quickly transition to a primary node if needed
log-replica-updates = 1

# --- Log Maintenance & Sizing ---
binlog-expire-logs-seconds = 604800
max-binlog-size = 100M

# --- Data Integrity & Crash Safety (ACID) ---
sync-binlog = 1
innodb-flush-log-at-trx-commit = 1

# --- Security & Networking ---
# Binds to the replica's specific internal IP address
bind-address = 192.168.12.160
----


. Restart the MariaDB service on the replica for changes to apply.
+
[source, console]
----
sudo systemctl restart mariadb
----



== Linking the replica to the primary and starting replication


----
The next step in the process is to link the replica to the primary server and start replication.
Since you are using MariaDB 11.8.8, this is done using modern Global Transaction Identifiers (GTID), which makes management much easier than old-style log file positions.
Run the following commands on the Replica server:

-- Step 1: Tell the replica to use GTID for tracking transactionsSET GLOBAL gtid_slave_pos = '';
-- Step 2: Configure the connection details to the Primary server-- Replace the parameters below with your actual primary IP and replication user password
CHANGE MASTER TO
  MASTER_HOST='10.0.0.10',
  MASTER_USER='repl_user',
  MASTER_PASSWORD='your_secure_password_here',
  MASTER_PORT=3306,
  MASTER_USE_GTID=current_pos;
-- Step 3: Start the replication worker threadsSTART SLAVE;

(Note: In MariaDB 11.8.8, CHANGE REPLICA TO and START REPLICA are also accepted aliases for these commands).
